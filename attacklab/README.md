# ReflexGuard 어택랩 — 보안 테스트·패치 체험 (교육용)

[← 프로젝트 README](../README.md) · 다음: [설치·실행 안내](INSTALL.md) · [시연 대본 (명령어 포함)](DEMO.md)

어택랩은 ReflexGuard의 보안 약점을 **내 PC 안의 격리된 도커 컨테이너에서 직접 확인하고 고쳐 보는** 교육용 실습 환경입니다. 보안 조치 전·후의 코드를 번갈아 띄워, 같은 요청이 어떻게 막히는지 기록(로그)으로 비교합니다. 보안이 실제로 어떻게 동작하는지 손으로 확인해 보고 싶을 때 읽으면 됩니다.

이 랩에서 다루는 약점은 ReflexGuard를 만들며 [함께 정리한 것들](../README.md#보안-기능)(인증 없음·평문 통신·요청 제한 없음 등)입니다. DVWA·OWASP Juice Shop처럼 '일부러 취약하게 둔 연습용 앱'과 같은 성격이고, 초점은 공격이 아니라 **탐지(로그)와 패치(방어)**입니다.

> **범위·안전**: 이 랩은 내가 만든 ReflexGuard를, 내 PC의 도커 컨테이너 안에서, `127.0.0.1`에만 열어 돌립니다. 다른 사람의 시스템이나 사내망·인터넷에 열지 마세요. 배운 내용은 내가 소유·운영하는 시스템을 지키는 데만 씁니다.

## 무엇을 하나

- 두 티어(따로 도는 묶음: 서버 쪽·클라이언트 쪽)를 격리된 도커 네트워크로 띄웁니다.
- 그 사이와 앞에 **감사 프록시**(오가는 요청을 가운데서 받아 넘겨주며 모두 기록하는 중계 프로그램)가 서서, 모든 요청을 로그로 남깁니다.
- 처음에는 모든 보호가 꺼진 **취약한 상태**입니다. 내 랩의 엔드포인트(요청을 받는 주소)에 `curl` 등으로 요청을 보내 보고, 감사 로그에서 결과를 관찰합니다.
- 고치는 방법은 둘입니다. 같은 요청이 어떻게 막히는지 로그로 비교하며 "패치 전/후"를 눈으로 확인합니다.
  - **앞단 완화**: `PATCH_*` 토글로 감사 프록시가 막게 한다.
  - **코드 조치**: `LAB_VERSION=after`로 보안 조치를 마친 본편 코드를 띄운다. 기본 `before`는 조치 직전에 얼려 둔 고정본([`vulnerable/`](vulnerable/README.md)).

## 구조

```
   내 브라우저 / curl / 보안 테스트 도구
            │  (127.0.0.1:8080 관제 화면, 8766 접속, 8443 체험·조작 화면, 8765 커넥톰)
            ▼
 ┌───────────────── server 컨테이너 (서버 티어) ───────────────────────────┐
 │  감사 프록시 ×2 ──로그──▶ attacklab/logs/audit-*.jsonl                  │
 │     │  (패치 토글: 토큰·속도·크기·Origin·읽기전용)                       │
 │     ▼                                                                   │
 │  관제 서버 · 체험·조작 포털 ──웹소켓──▶ Webots 대역 (명령 기록)          │
 │  (모두 127.0.0.1 전용 — 바깥에는 프록시만 보인다)                       │
 └─────────────────────────────────────────────────────────────────────┘
            ▲ 상태·사건·명령 (TCP 8766, 평문 JSON)
            │
 ┌───────────────── client 컨테이너 (클라이언트 티어) ──────────────────┐
 │  사용자(휠체어) 시뮬레이션 ──커넥톰 통신(TCP)──▶ 감사 탭 ─▶ 연산 서버  │
 │  (녹화 영상을 파이프라인에 흘려 '정상 트래픽'을 만든다)                │
 └─────────────────────────────────────────────────────────────────────┘
```

**서버 티어** `server`

- 관제 서버 + 체험·조작 포털(`demo/server.py`) + Webots 대역 + 감사 프록시.
- 서버들은 컨테이너 안(127.0.0.1)에만 열고, 바깥에는 프록시만 노출합니다. 그래서 **모든 요청이 로그를 거칩니다**.
- 랩에는 Webots가 없습니다. 대신 Webots 대역(Webots 흉내만 내는 가짜 프로그램)이 그 자리에서, 포털이 이어 준 웹소켓의 출처(`Origin`)와 조작 명령을 기록합니다.
- 체험·조작 포털은 랩에서 HTTP로 엽니다(127.0.0.1이라 카메라도 됨).

**클라이언트 티어** `client`

- 사용자 시뮬레이션(`client/robot_sim.py`) + 커넥톰 연산 서버 + 커넥톰 통신 감사 탭(커넥톰 통신만 기록하는 감사 프록시).
- 연산 서버도 관제 서버에 붙어 접속 상태와 뉴런 발화율을 보냅니다. 관제 화면의 로봇 카드에서 '루밍 동작 보기'를 펼치면 LPLC2 → DNp01이 움직이는 것이 보입니다(조치 후 본편).
- 끊임없이 정상 상태를 관제 서버로 보내, 내 테스트 트래픽과 비교할 바탕을 만듭니다.

| 파일 | 하는 일 |
|---|---|
| `docker-compose.yml` | 두 티어를 격리 네트워크로, 포트는 `127.0.0.1`에만 묶어 띄운다 |
| `lab_version.sh` | `LAB_VERSION`(before/after)으로 돌릴 코드 폴더를 고른다 |
| `Dockerfile` | 두 티어가 같이 쓰는 이미지 (`python:3.10-slim` 다이제스트 고정, numpy 해시 확인, 비루트 사용자로 실행) |
| `vulnerable/` | 보안 조치 전 고정본 (개발 저장소 dryingho/reflexguard의 커밋 `2581ffb`). 일부러 취약 — 고치지 않는다 ([설명](vulnerable/README.md)) |
| `server/audit_proxy.py` | 감사 프록시. 모든 접속·HTTP 요청·에이전트 줄(로봇·연산 서버가 보내는 JSON 한 줄)을 JSONL로 기록하고, `PATCH_*`로 방어를 켠다. 요청은 바꾸지 않고, 막을 때만 짧은 응답을 돌려준다 |
| `server/webots_stub.py` | Webots 대역. 체험·조작 포털이 이어 준 웹소켓의 출처와 명령을 기록 |
| `server/entrypoint.sh` | 관제 서버·체험·조작 포털·Webots 대역(컨테이너 안) + 프록시 둘(밖)을 함께 띄운다 |
| `client/robot_sim.py` | Webots 없이 녹화 영상으로 휠체어 PC 파이프라인을 돌려 관제 서버에 접속(사용자 시뮬레이션·커넥톰 통신). 상태와 명령 처리(커넥톰·안전 스위치·비상 정지·속도 제한·처음부터 다시)는 Webots 컨트롤러와 같다 — 받은 명령이 로봇을 실제로 멈춘다 |
| `client/data/` | 사용자 시뮬레이션이 흘려 넣는 Webots 주행 녹화 3개 (`LAB_CLIP`: `wall`·`person`·`sidewalk`) |
| `client/entrypoint.sh` | 연산 서버 + 통신 탭 + 로봇 시뮬레이션을 함께 띄운다 |
| `INSTALL.md` | 우분투에서 도커 설치부터 랩을 띄우고 끄기까지 (준비물, 실행·확인, 문제 해결) |
| `DEMO.md` | 시연 대본 — 조치 전·후 비교 명령어와 결과 |
| `exercises/` | 약점마다: 관찰(보안 테스트) → 패치 → 검증 |
| `logs/` | 감사 로그가 모이는 곳 (`audit-*.jsonl`) |

## 빠른 시작

도커와 도커 컴포즈가 필요합니다. 저장소 루트가 빌드 컨텍스트(이미지를 만들 때 쓰는 폴더)입니다. 도커가 없는 우분투라면 [설치·실행 안내](INSTALL.md)를 먼저 따라가세요.

```bash
cd attacklab
docker compose up --build        # 취약한 상태로 두 티어가 뜬다
```

- 관제 화면: <http://127.0.0.1:8080/live>
- 체험·조작 화면: <http://127.0.0.1:8443/>
- 조치 후 본편으로: `LAB_VERSION=after docker compose up --build`
- 로그 보기(다른 터미널): `docker compose logs -f` 또는 `tail -f logs/audit-*.jsonl`

끄기: `docker compose down`.

## 로그 수집 (이 랩의 핵심)

감사 프록시는 오가는 모든 것을 한 줄짜리 JSON으로 파일과 콘솔에 남깁니다.

파일은 어디서 남겼는지에 따라 나뉩니다.

| 파일 | 어디서 |
|---|---|
| `audit-<시각>` | 관제 서버 |
| `audit-portal-*` | 체험·조작 포털 |
| `audit-webots-*` | Webots 대역 |
| `audit-connectome-*` | 커넥톰 통신 |

줄마다 종류(`kind`)가 붙습니다.

| kind | 뜻 |
|---|---|
| `http` / `http-reply` | 들어온 HTTP 요청(메서드·경로·헤더·본문 미리보기)과 관제 서버의 응답 상태 |
| `agent-connect` / `agent-line` / `agent-close` | 로봇·연산 서버 접속과 오가는 JSON 줄(양방향) |
| `webots-connect` / `webots-command` / `webots-close` | Webots 대역에 닿은 웹소켓의 출처(`origin`)와 조작 명령 |
| `blocked` | 패치 규칙에 막힌 요청과 **사유**(`by`: require_token·rate_limit·read_only·max_body·allowed_hosts) |
| `listen` / `start` / `error` | 프록시 켜짐·오류 |

토큰·암호 같은 값은 로그에서 `<가림>`으로 가립니다. 보기 좋게 보려면:

```bash
tail -f logs/audit-*.jsonl | python -m json.tool --json-lines   # 또는 jq
```

## 패치 토글

기본은 모두 꺼짐(취약)입니다. 셸에서 앞에 붙이거나 `attacklab/.env`에 적고 다시 올립니다.

```bash
PATCH_REQUIRE_TOKEN=1 PATCH_TOKEN=lab-secret REFLEXGUARD_DASHBOARD_TOKEN=lab-secret \
  docker compose up --build
```

| 변수 | 켜면 하는 일 | 막는 약점 |
|---|---|---|
| `PATCH_REQUIRE_TOKEN=1` + `PATCH_TOKEN=…` | 올바른 토큰 없는 HTTP·접속을 막는다(401) | 인증 없음 |
| `PATCH_READ_ONLY=1` | GET 외 메서드(POST 등)를 막는다(403) | 명령 위조 |
| `PATCH_RATE_LIMIT_RPS=<수>` | 한 IP가 초당 그 이상 보내면 막는다(429) | 요청 폭주(DoS, 서비스 거부) |
| `PATCH_MAX_BODY=<바이트>` | 본문이 그보다 크면 막는다(413) | 과대 입력 |
| `PATCH_ALLOWED_HOSTS=a,b` | Host/Origin이 목록에 없으면 막는다(403) | 다른 출처에서의 요청 |
| `REFLEXGUARD_DASHBOARD_TOKEN=…` | **관제 서버 자체**가 토큰을 확인(앱단 패치 — 프록시를 우회해도 막힘) | 인증 없음(심층 방어) |

**앞단 완화와 앱단 패치의 차이**

- `PATCH_*`는 프록시(앞단)에서 막는 완화입니다. 웹 방화벽(WAF)이 하는 일과 비슷합니다.
- `REFLEXGUARD_DASHBOARD_TOKEN`은 앱 자체를 고치는 패치입니다.
- 실제 운영에서는 둘을 겹쳐 씁니다. 한 겹이 뚫려도 다음 겹이 막도록 하는 것을 심층 방어라고 합니다.
- 연습 때 '정상 클라이언트'(client 티어)가 계속 통과하려면 두 토큰 값을 같게 맞춰 주세요.

## 본편의 보안 조치 단계

`LAB_VERSION=after`로 띄우는 본편은 아래 14단계를 거쳐 고친 코드입니다. 연습 문서의 '실제 반영'에 나오는 'n단계'가 이 표의 번호입니다. 기준은 KISA 소프트웨어 개발보안 가이드와 SW 공급망 보안 가이드라인입니다(조치 전 '취약' 23개·'부분' 16개 → 조치 후 0개).

| 단계 | 무엇을 막나 | 관련 연습 |
|---|---|---|
| 1 요청 위조 막기 | 다른 사이트가 사용자의 브라우저를 빌려 명령을 보내는 것 — JSON 본문만, 다른 `Origin` 거부 | 2 · 5 |
| 2 노출 축소 | 체험·조작 포털이 기본으로 다른 기기에 열려 있는 것 — 기본 127.0.0.1 | 5 |
| 3 모든 진입점 인증 | 토큰 없이 보거나 명령하는 것, 보기만 할 사람이 명령까지 하는 것 — 토큰 기본 켜기, 보기 전용 분리 | 1 · 2 · 4 · 5 |
| 4 입력·자원 한도 | 요청 폭주·토큰 추측·이상한 값으로 서버를 멈추게 하는 것 — 속도 제한, 5번 틀리면 잠금, 줄 길이·접속 수 상한 | 3 |
| 5 전송·저장 | 화면에 남의 스크립트가 끼어드는 것, 기록을 다른 계정이 읽는 것 — 보안 헤더(CSP 등), 기록 권한 0600 | — |
| 6 공급망 | 외부 라이브러리 바꿔치기·알려진 취약점 — 버전·해시 고정, SBOM, pip-audit·bandit | — |
| 7 남은 위험 | 다른 PC와의 통신 엿보기·가짜 서버, 기록 몰래 고치기 — TLS + 인증서 지문 고정, 기록 HMAC 사슬, Webots 루프백 | 4 |
| 8 장치별 자격증명·명령 서명 | 가짜 휠체어로 붙기, 가로챈 명령 다시 보내기 — 장치 열쇠, 명령 서명·순번 | 2 |
| 9 커넥톰 데이터 서명 | 회로 파일을 몰래 고쳐 회피 반사를 약하게 만드는 것 — Ed25519 서명 확인 | — |
| 10 엄격한 입력·세션 수명·느린 요청 | 모르는 칸 섞기, 접속만 붙잡기, 1바이트씩 천천히 보내기 — 모르는 칸 거부, 쉬는 접속 닫기, 요청 대기 시간 | 3 |
| 11 CSRF 토큰·Host 허용 목록 | 요청 위조를 한 겹 더, 엉뚱한 주소 이름으로 속이기(DNS 리바인딩) | 2 |
