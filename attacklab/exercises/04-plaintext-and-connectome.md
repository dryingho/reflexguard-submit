# 연습 4 — 평문 통신과 커넥톰 통신 관찰

[← 연습 3 — 요청 폭주](03-flooding.md) · 다음: [연습 5 — 다른 사이트의 웹소켓](05-cross-site-websocket.md)

로봇과 서버가 주고받는 내용이 평문(암호화하지 않은 글)이라 그대로 보인다는 것을 감사 로그로 확인하고, 토큰으로 가짜 접속을 막아 봅니다.

## 약점
- **평문 통신**: 관제 서버 접속(TCP 8766)과 커넥톰 통신(TCP 8765)은 암호화가 없습니다. 같은 네트워크에서 내용을 엿보거나 바꿔치기할 수 있습니다.
- **커넥톰 통신의 신뢰 경계**: 로봇은 연산 서버의 답을 믿고 움직입니다. 연산 서버 포트에 인증이 없으면, 가짜 서버나 중간자(통신 중간에서 엿보거나 바꾸는 사람)가 '위험 없음' 같은 답을 흘려 보호를 무력화할 여지가 있습니다.
  - 관제 서버로 가는 쪽은 로봇 → 서버 보고라 방향이 반대지만, 통신이 평문이라는 점은 같습니다.

## 관찰 (보안 테스트)
이번엔 공격이 아니라 **로그로 평문을 눈으로 확인**합니다. 감사 프록시가 오가는 JSON 줄을 그대로 남기므로, 통신이 암호화되지 않았음을 직접 봅니다.

```bash
# 대시보드로 가는 로봇의 상태 보고 (서버 티어)
grep agent-line logs/audit-*.jsonl | head -3
# 커넥톰 통신 (클라이언트 티어 탭)
docker compose logs client | grep "커넥톰 통신" | head -3
```

- `line` 칸에 좌표·위험도·명령이 평문으로 보입니다. 암호화돼 있다면 여기서 내용이 보이지 않아야 합니다.
- 토큰 같은 값은 로그에서 `<가림>` 처리되지만, 통신 자체는 평문이라는 점이 드러납니다.

## 패치(완화)와 한계
이 랩의 토글은 앞단에서의 **인증·속도·크기** 완화에 집중합니다. 암호화(TLS)는 보통 앞단에 TLS 종료 프록시(바깥과는 암호화로 통신하고, 안쪽 서버에는 풀어서 넘겨주는 중계 서버)를 두어 해결합니다. 이 랩에서는 다음을 해 봅니다.

- **접속 범위 좁히기**: compose가 포트를 `127.0.0.1`에만 묶었습니다. 그래서 바깥 네트워크에서는 평문이라도 애초에 닿지 못합니다. 이것이 1차 방어입니다.
- **인증으로 가짜 접속 차단**: `PATCH_REQUIRE_TOKEN`으로 접속(8766)에 토큰을 요구하면, 토큰 없는 가짜 로봇·서버의 접속이 막힙니다(로그 `blocked / require_token`).

```bash
docker compose down
PATCH_REQUIRE_TOKEN=1 PATCH_TOKEN=lab-secret REFLEXGUARD_DASHBOARD_TOKEN=lab-secret \
  docker compose up --build
```

## 검증
```bash
# 토큰 없이 접속을 흉내 내 보기 (대시보드 접속 포트에 hello 한 줄)
printf '{"type":"hello","role":"webots","name":"fake"}\n' | \
  timeout 2 nc 127.0.0.1 8766 | head -c 120; echo
```

- 패치 전: 접속이 받아들여집니다.
- 패치 후: `{"type":"error","message":"bad token"}`로 끊기고, 로그에 `blocked / require_token (proto:agent)`.
- 조치 후 본편(`LAB_VERSION=after`):
  - 앞단 패치 없이도 관제 서버가 `bad token`으로 끊습니다.
  - 커넥톰 연산 서버(8765)도 첫 줄이 맞는 토큰(`{"type":"auth","token":…}`)이 아니면 `bad token`으로 끊습니다. 가짜 휠체어가 연산 서버를 마음대로 쓰지 못합니다:

```bash
printf '{"type":"step","seq":1,"dt_ms":32}\n' | timeout 2 nc 127.0.0.1 8765 | head -c 120; echo
```

  (랩에서는 통신이 평문인 채로 남습니다. 본편은 [7단계](../README.md#본편의-보안-조치-단계)에서 다른 PC와의 통신을 TLS로 암호화했지만, 같은 PC 안(127.0.0.1)의 평문은 그대로 받습니다. 랩의 서버들은 컨테이너 안 127.0.0.1에서 감사 프록시 뒤에 있으므로 이 경우에 해당합니다.)

## 실제 반영
- 운영에서는 통신을 TLS로 암호화하고, 접속은 인증 뒤에 둡니다.
  - 본편은 다른 PC와의 통신에 서버 자체 TLS와 인증서 지문 고정을 씁니다([7단계](../README.md#본편의-보안-조치-단계)). 다른 PC의 기계 접속은 등록된 클라이언트 인증서까지 확인합니다(mTLS, [12단계](../README.md#본편의-보안-조치-단계)). 정리는 [README의 보안 기능](../../README.md#보안-기능).
- 휠체어 PC는 연산 서버가 보낸 답의 값 범위를 확인합니다(무한대·NaN 거르기).
- 답이 늦거나 끊기면 '판단 없음 → 안전 정지'로 처리합니다(`wheelchair/brain_client.py`).
- 이처럼 '통신이 깨져도 안전한 쪽으로' 동작하게 두는 것이 통신 보안과 함께 가는 설계입니다.
